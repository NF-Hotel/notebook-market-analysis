## Purpose

Give the market analysis service the analysis that the website needs. NFHotel MIL-004 deployed `NF-Hotel/Notebook_Market_Analysis` and NFHotel MIL-026 was built on its `POST /analyze?insights=true`. That repository is gone from GitHub: its successor `NF-Hotel/notebook-market-analysis` is a new service of which only `/health` and the holiday calendar are built, so the image of the old pinned commit (`6c11cbf2`) can no longer be built and the release check of pull request 180 fails. The milestone builds the missing part in the new service, in its Clean Architecture layers: the nine analyses of the bookings (lead time, holidays, seasonality, cancellations, room value, guest mix, occupancy, occupancy on holidays, correlations), the AI executive summary and suggestions of each, and a run API (start, state, result) behind the key `X-API-Key`. This is the same phase as NFHotel MIL-028, planned here because the code goes in this repository and its plan-first gate needs a milestone here.

## Deliverable

- **Contract first.** `openapi/market-contract.yaml` of the market analysis service gets the run paths (`POST /api/v1/market-analysis/runs`, `GET /api/v1/market-analysis/runs/{id}`, `GET /api/v1/market-analysis/runs/{id}/result`) with the booking as input (the fields of `MarketBookingDto` of the website, an optional period) and result schema 1.1 as output (the sample `docs/test-data/market-analysis-result.json` of this repository is the first test file of both sides).
- The nine analyses over the bookings that are posted, in the domain and application layers, with unit tests; no notebook library in the image: the six of the first version (lead time, holidays, seasonality, cancellations, room value, guest mix) and three new ones, occupancy (the share of room nights that are taken, by month and overall), occupancy on holidays (the same share on holiday days against other days) and correlations (the Spearman correlation between the numeric booking fields and cancelled, as a matrix). The run request carries `room_count` (the rooms of the hotel), because the bookings do not say how many rooms there are; the result gives for each analysis the formula it used and what it cannot say (`limitations`).
- An AI port and adapters (Ollama and LM Studio, as `docs/architecture.md` of this repository plans) that write an `insight` with `executive_summary` and `improvement_suggestions` for every analysis, and one observation for every chart, what the AI sees in that series (`observations`, each with the `series` path of the group figures it reads, its text and its evidence), written in the same request as the insight of the analysis so that a run stays within its 12 minutes, with a guardrail that gives `GUARDRAIL_REJECTED` and leaves the numbers untouched.
- **Room revenue (task 7).** The room value analysis gets `room_revenue`: the sum of price per night times nights of the bookings that are not cancelled, in the price units of the input, with a mean for each booking and a series for each month of arrival; result schema 1.2, which adds the field and changes nothing else, so a client of schema 1.1 still reads the result. The old estimate stays and keeps its notice that it is not revenue; `room_revenue` says in its own limitation that taxes, fees, discounts, extras and the currency are not known.
- **Useful AI texts and a forecast (task 8).** Every chart gets its own AI text: a summary of two to three sentences and one to three recommendations, each with the numbers it rests on (a request for each chart, not one for the whole analysis, so a small model keeps to the point). The service, not the model, calculates a forecast for the next 3 to 6 months of arrivals, occupancy and room revenue from the seasonal pattern of the bookings, with a band for the uncertainty, in result schema 1.2; the model only comments on those numbers. The guardrail lets a forecast through when it is the figure of the service and is marked as a projection of the history, and still refuses a promise, a cause and a number the model made up.
- **AI texts as Markdown (task 9).** The summaries, recommendations and observations of the AI are Markdown (a short lead paragraph, one list item for each chart that names the chart in bold, a list of recommendations); the contract says the text fields are Markdown, raw HTML is removed from a model answer before the guardrail and before storage, and the prompt version is raised.
- **Overall interpretation (task 10).** `insights.overall` holds one Markdown interpretation of the whole run (key points, what they mean together, two to four recommendations, caveats) under the same guardrail, with a fallback built from the figures and marked as such when the AI is off or the answer is rejected.
- **Guardrail: dates and counts (task 11).** A year after a month name and the number of months or points of a chart are not figures that must be found in the series, so the texts of month charts are no longer rejected for them; nothing else in the guardrail is relaxed.
- A background run with one run at a time, a state (`queued`, `running`, `completed`, `failed`) and the result kept in the output volume.
- Deploy: the image and `deploy/docker-compose.yml` of this repository start the service with the AI settings in its env file; the Dockerfile still needs no network at build time other than the package index.
- Unchanged: the holiday calendar paths and their contract.
